[CENTER][SIZE=5][B][COLOR=#FFD700]⚙️  2.  ARCHITECTURE & CACHING ENGINE[/COLOR][/B][/SIZE][/CENTER]
[COLOR=#FFD700]━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━[/COLOR]

[B][COLOR=#FFFFFF]How the O(1) Intercept Engine works:[/COLOR][/B]

[LIST]
[*][B][COLOR=#FFD700]Dynamic Wrapping:[/COLOR][/B] [COLOR=#AAAAAA]VaultX intercepts any incoming economy plugin (e.g. EssentialsX) at the highest service priority and wraps it in an [/COLOR][COLOR=#E0E0E0]OptimizedEconomy[/COLOR][COLOR=#AAAAAA] decorator. This works both at startup and dynamically when plugins register themselves later.[/COLOR]

[*][B][COLOR=#FFD700]Online-Only Memory Cache:[/COLOR][/B] [COLOR=#AAAAAA]Balances for online players are cached in a [/COLOR][COLOR=#E0E0E0]ConcurrentHashMap[/COLOR][COLOR=#AAAAAA]. A configurable TTL ([/COLOR][COLOR=#E0E0E0]cache-ttl-ms[/COLOR][COLOR=#AAAAAA], default: 1000ms) prevents stale values if other plugins modify balances directly. No stale data risk for offline players.[/COLOR]

[*][B][COLOR=#FFD700]Offline Player Balance Cache:[/COLOR][/B] [COLOR=#AAAAAA]Balances queried for offline players are cached in a thread-safe cache with a 10-second TTL to prevent database spam during high-volume lookups.[/COLOR]

[*][B][COLOR=#FFD700]Automatic Cache Invalidation:[/COLOR][/B] [COLOR=#AAAAAA]Every deposit or withdrawal instantly updates the memory cache in real-time. On player disconnect, their cache slot is fully purged.[/COLOR]

[*][B][COLOR=#FFD700]Balance Pre-Warming:[/COLOR][/B] [COLOR=#AAAAAA]When a player connects, their main balance is loaded synchronously (ensuring immediate availability for delegate economy plugins) while custom currency balances are pre-loaded asynchronously off the main thread.[/COLOR]

[*][B][COLOR=#FFD700]ServicePriority.Highest:[/COLOR][/B] [COLOR=#AAAAAA]VaultX forces its wrapper to register at the highest service priority, ensuring all downstream plugins always hit the fast-track cached system first.[/COLOR]

[*][B][COLOR=#FFD700]SQLite WAL Mode:[/COLOR][/B] [COLOR=#AAAAAA]When using SQLite storage, VaultX automatically configures Write-Ahead Logging ([/COLOR][COLOR=#E0E0E0]PRAGMA journal_mode=WAL[/COLOR][COLOR=#AAAAAA]) and [/COLOR][COLOR=#E0E0E0]PRAGMA synchronous=NORMAL[/COLOR][COLOR=#AAAAAA]. This delivers up to 10x–100x faster write speeds and allows non-blocking concurrent reads.[/COLOR]

[*][B][COLOR=#FFD700]Thread-Safe MySQL Connection Pool:[/COLOR][/B] [COLOR=#AAAAAA]When using MySQL/MariaDB, an internal connection pool (max: 10 connections, pre-warmed with 3) handles asynchronous transactions concurrently without blocking the main server thread.[/COLOR]

[*][B][COLOR=#FFD700]Functional Query Templates:[/COLOR][/B] [COLOR=#AAAAAA]Standardized database interactions using [/COLOR][COLOR=#E0E0E0]DbConsumer[/COLOR][COLOR=#AAAAAA] and [/COLOR][COLOR=#E0E0E0]DbFunction[/COLOR][COLOR=#AAAAAA] patterns guarantee that connections are always safely returned to the pool, preventing memory leaks and connection exhaustion.[/COLOR]

[*][B][COLOR=#FFD700]Database Query Indexing:[/COLOR][/B] [COLOR=#AAAAAA]Composite indexes [/COLOR][COLOR=#E0E0E0](uuid, id)[/COLOR][COLOR=#AAAAAA] are added on [/COLOR][COLOR=#E0E0E0]player_transactions[/COLOR][COLOR=#AAAAAA] and [/COLOR][COLOR=#E0E0E0]security_audits[/COLOR][COLOR=#AAAAAA] tables to eliminate full-table scans. On MySQL/MariaDB, the plugin checks [/COLOR][COLOR=#E0E0E0]information_schema[/COLOR][COLOR=#AAAAAA] before index creation to guarantee backwards compatibility.[/COLOR]

[*][B][COLOR=#FFD700]Asynchronous Batch Writer (VaultX-BatchWriter):[/COLOR][/B] [COLOR=#AAAAAA]A background daemon thread drains transaction, audit, and sync queues every 1 second, batching updates within single SQL transactions to speed up writes by 50x+ and eliminate disk contention on SQLite/MySQL.[/COLOR]
[/LIST]

[CENTER][SIZE=5][B][COLOR=#FFD700]📡  3.  REDIS CROSS-SERVER SYNCHRONIZATION[/COLOR][/B][/SIZE][/CENTER]
[COLOR=#FFD700]━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━[/COLOR]

[COLOR=#AAAAAA]VaultX integrates a production-grade Redis Pub/Sub synchronization layer to keep balances consistent across an entire network of servers in real-time.[/COLOR]

[LIST]
[*][B][COLOR=#FFD700]Balance Sync:[/COLOR][/B] [COLOR=#AAAAAA]Every transaction is published to a Redis Pub/Sub channel (default: [/COLOR][COLOR=#E0E0E0]vaultx:economy:sync[/COLOR][COLOR=#AAAAAA]). All connected servers receive the update and refresh their local caches instantly.[/COLOR]

[*][B][COLOR=#FFD700]Jedis Connection Pool:[/COLOR][/B] [COLOR=#AAAAAA]Uses a configurable Jedis pool (default: [/COLOR][COLOR=#E0E0E0]max-connections: 16[/COLOR][COLOR=#AAAAAA]) with a configurable [/COLOR][COLOR=#E0E0E0]connection-timeout-ms[/COLOR][COLOR=#AAAAAA] (default: 2000ms).[/COLOR]

[*][B][COLOR=#FFD700]Heartbeat Check:[/COLOR][/B] [COLOR=#AAAAAA]A background task verifies Redis connectivity every [/COLOR][COLOR=#E0E0E0]heartbeat-interval-seconds[/COLOR][COLOR=#AAAAAA] (default: 5s). If Redis goes offline, VaultX automatically switches to database failover mode without any player impact.[/COLOR]

[*][B][COLOR=#FFD700]Exponential Backoff Reconnect:[/COLOR][/B] [COLOR=#AAAAAA]If Redis goes offline, the reconnect delay scales exponentially ([/COLOR][COLOR=#E0E0E0]baseDelay × 1.5^attempts[/COLOR][COLOR=#AAAAAA]) up to a 60-second ceiling, with ±20% random jitter to prevent reconnect storms on large proxy networks.[/COLOR]

[*][B][COLOR=#FFD700]Auto-Reconnect Failover:[/COLOR][/B] [COLOR=#AAAAAA]When Redis comes back online, queued balance updates stored in the local database are automatically flushed to Redis.[/COLOR]

[*][B][COLOR=#FFD700]Distributed Account Freeze:[/COLOR][/B] [COLOR=#AAAAAA]Frozen player accounts are synced across all servers via a Redis Set ([/COLOR][COLOR=#E0E0E0]vaultx:frozen_players[/COLOR][COLOR=#AAAAAA]) and Pub/Sub events.[/COLOR]

[*][B][COLOR=#FFD700]Distributed Mutex Locks:[/COLOR][/B] [COLOR=#AAAAAA]Atomic Redis locks ([/COLOR][COLOR=#E0E0E0]vaultx:lock:[uuid]:[currency][/COLOR][COLOR=#AAAAAA]) prevent race conditions when two servers attempt to modify the same account simultaneously.[/COLOR]

[*][B][COLOR=#FFD700]Leaderboard ZSET:[/COLOR][/B] [COLOR=#AAAAAA]Every balance update also writes to Redis Sorted Sets ([/COLOR][COLOR=#E0E0E0]vaultx:leaderboard:[currency][/COLOR][COLOR=#AAAAAA]) to maintain a real-time global wealth ranking.[/COLOR]

[*][B][COLOR=#FFD700]Latest-Write-Wins (LWW) Reconciliation:[/COLOR][/B] [COLOR=#AAAAAA]When a server reconnects after a Redis outage, VaultX compares local database timestamps against Redis global values and applies the most recent write, preventing balance divergence and money duplication.[/COLOR]

[*][B][COLOR=#FFD700]Cross-Server Escrow:[/COLOR][/B] [COLOR=#AAAAAA]Funds involved in cross-server trades are locked in a pending state using Redis distributed mutex locks, with automatic refund tasks checking for expired escrows.[/COLOR]
[/LIST]

[CENTER][SIZE=5][B][COLOR=#FFD700]💾  4.  LOCAL DATABASE STORAGE & FAILOVER[/COLOR][/B][/SIZE][/CENTER]
[COLOR=#FFD700]━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━[/COLOR]

[COLOR=#AAAAAA]VaultX supports [B]SQLite[/B] (local) or [B]MySQL / MariaDB[/B] (shared) as its resilient failover layer. If Redis goes offline, the plugin falls back to database storage automatically. All operations are fully thread-safe and run asynchronously.[/COLOR]

[B][COLOR=#FFFFFF]Managed database tables:[/COLOR][/B]
[LIST]
[*][B][COLOR=#FFD700]pending_syncs:[/COLOR][/B] [COLOR=#AAAAAA]Queues balance modifications made while Redis is offline. These are flushed to Redis as soon as connectivity is restored.[/COLOR]
[*][B][COLOR=#FFD700]local_banks:[/COLOR][/B] [COLOR=#AAAAAA]Fallback bank storage, updated on every bank transaction and backed up periodically.[/COLOR]
[*][B][COLOR=#FFD700]security_audits:[/COLOR][/B] [COLOR=#AAAAAA]Permanent history of all security incidents, rate limit infractions, and freeze/unfreeze events. Queried via [/COLOR][COLOR=#E0E0E0]/eco admin audit[/COLOR][COLOR=#AAAAAA].[/COLOR]
[*][B][COLOR=#FFD700]custom_currency_balances:[/COLOR][/B] [COLOR=#AAAAAA]Persists player balances for all custom currencies (Gems, Tokens, etc.) with a [/COLOR][COLOR=#E0E0E0]last_updated[/COLOR][COLOR=#AAAAAA] timestamp to support LWW reconciliation.[/COLOR]
[*][B][COLOR=#FFD700]player_transactions:[/COLOR][/B] [COLOR=#AAAAAA]Detailed ledger of all deposits and withdrawals with automatic category tagging (SHOP, QUEST, ADMIN, JOB) based on the caller namespace.[/COLOR]
[*][B][COLOR=#FFD700]local_escrows:[/COLOR][/B] [COLOR=#AAAAAA]Stores active, completed, or refunded escrow transactions to guarantee transactional integrity without Redis.[/COLOR]
[*][B][COLOR=#FFD700]pending_webhooks:[/COLOR][/B] [COLOR=#AAAAAA]Persists failed or rate-limited Discord webhook alerts for asynchronous retry via exponential backoff.[/COLOR]
[*][B][COLOR=#FFD700]daily_analytics:[/COLOR][/B] [COLOR=#AAAAAA]Aggregates daily statistics of money created and destroyed across categories to monitor inflation trends.[/COLOR]
[/LIST]
[COLOR=#AAAAAA]All security firewall events are also appended to a plain-text [B]security_audit.log[/B] file in the plugin directory.[/COLOR]

[CENTER][SIZE=5][B][COLOR=#FFD700]🛡️  5.  SECURITY FIREWALL[/COLOR][/B][/SIZE][/CENTER]
[COLOR=#FFD700]━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━[/COLOR]

[COLOR=#AAAAAA]VaultX includes a multi-layer transaction security system protecting your economy from exploits, duplication glitches, and bot abuse.[/COLOR]

[SIZE=3] [/SIZE]

[B][COLOR=#FFFFFF]Layer 1 — Rate Limiter (Anti-Duplication Shield):[/COLOR][/B]
[LIST]
[*][COLOR=#AAAAAA]Counts transactions per second for each player UUID.[/COLOR]
[*][COLOR=#AAAAAA]If a player exceeds [/COLOR][COLOR=#E0E0E0]max-transactions-per-second[/COLOR][COLOR=#AAAAAA] (default: [B]20[/B]), their account is blocked for [/COLOR][COLOR=#E0E0E0]cooldown-seconds[/COLOR][COLOR=#AAAAAA] (default: [B]5s[/B]).[/COLOR]
[*][COLOR=#AAAAAA]Triggers a Discord Webhook alert (if enabled) classified as [B]RATE_LIMIT_EXCEEDED 🟡[/B].[/COLOR]
[/LIST]

[B][COLOR=#FFFFFF]Layer 2 — Transaction Firewall:[/COLOR][/B]
[LIST]
[*][B][COLOR=#FFD700]Account Freeze Check:[/COLOR][/B] [COLOR=#AAAAAA]All transactions from frozen accounts are blocked instantly.[/COLOR]
[*][B][COLOR=#FFD700]Single Transaction Limit:[/COLOR][/B] [COLOR=#AAAAAA]Any single deposit or withdrawal exceeding [/COLOR][COLOR=#E0E0E0]max-single-transaction[/COLOR][COLOR=#AAAAAA] (default: [B]10,000,000[/B]) is blocked. If [/COLOR][COLOR=#E0E0E0]auto-freeze: true[/COLOR][COLOR=#AAAAAA], the player is frozen automatically. Triggers a 🔴 [B]TRANSACTION_BLOCKED[/B] alert.[/COLOR]
[*][B][COLOR=#FFD700]Large Transaction Alert:[/COLOR][/B] [COLOR=#AAAAAA]Transactions exceeding [/COLOR][COLOR=#E0E0E0]large-transaction-threshold[/COLOR][COLOR=#AAAAAA] (default: [B]500,000[/B]) trigger a Discord alert even if the transaction is allowed.[/COLOR]
[*][B][COLOR=#FFD700]Heuristic Spike Detection:[/COLOR][/B] [COLOR=#AAAAAA]Tracks deposits over a rolling window (default: [B]60s[/B]). If the total exceeds the player's baseline multiplied by [/COLOR][COLOR=#E0E0E0]factor[/COLOR][COLOR=#AAAAAA] (default: [B]5.0[/B]) and is above [/COLOR][COLOR=#E0E0E0]minimum-threshold[/COLOR][COLOR=#AAAAAA] (default: [B]10,000[/B]), the player is frozen. Triggers a 🔴 [B]SPIKE_DETECTED[/B] alert.[/COLOR]
[/LIST]

[B][COLOR=#FFFFFF]Discord Webhook Alerts:[/COLOR][/B]
[COLOR=#AAAAAA]Security events are sent as rich Discord Embeds to a staff channel. Each alert includes:[/COLOR]
[LIST]
[*][COLOR=#AAAAAA]Alert type: [B]FREEZE 🔴[/B], [B]UNFREEZE 🟢[/B], [B]TRANSACTION_BLOCKED 🔴[/B], [B]SPIKE_DETECTED 🔴[/B], [B]RATE_LIMIT_EXCEEDED 🟡[/B][/COLOR]
[*][COLOR=#AAAAAA]Player name and UUID[/COLOR]
[*][COLOR=#AAAAAA]Detailed reason and amounts[/COLOR]
[*][COLOR=#AAAAAA]Timestamp[/COLOR]
[/LIST]
[COLOR=#AAAAAA]To enable, set [/COLOR][COLOR=#E0E0E0]security.firewall.discord-webhook.enabled: true[/COLOR][COLOR=#AAAAAA] and paste your webhook URL in [/COLOR][COLOR=#E0E0E0]config.yml[/COLOR][COLOR=#AAAAAA].[/COLOR]

[B][COLOR=#FFFFFF]Resilient Webhook Retry Queue:[/COLOR][/B]
[LIST]
[*][COLOR=#AAAAAA]If Discord is rate-limited (HTTP 429) or offline, the payload is saved in the [/COLOR][COLOR=#E0E0E0]pending_webhooks[/COLOR][COLOR=#AAAAAA] table.[/COLOR]
[*][COLOR=#AAAAAA]An async task retries every 10 seconds using Exponential Backoff ([/COLOR][COLOR=#E0E0E0]15s × 2^attempts[/COLOR][COLOR=#AAAAAA]).[/COLOR]
[*][COLOR=#AAAAAA]Limited to 10 retry attempts before discarding to prevent database bloat.[/COLOR]
[/LIST]

[CENTER][SIZE=5][B][COLOR=#FFD700]💱  6.  MULTI-CURRENCY SYSTEM[/COLOR][/B][/SIZE][/CENTER]
[COLOR=#FFD700]━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━[/COLOR]

[COLOR=#AAAAAA]VaultX natively extends the Vault Economy API with full multi-currency support, compatible with any plugin using the [B]MultiCurrencyEconomy[/B] interface.[/COLOR]

[LIST]
[*][B][COLOR=#FFD700]Supported Currencies:[/COLOR][/B] [COLOR=#AAAAAA]The default currency is always available. Additional currencies (e.g. [B]Gems[/B], [B]Tokens[/B]) are defined in [/COLOR][COLOR=#E0E0E0]currency-exchange.rates[/COLOR][COLOR=#AAAAAA].[/COLOR]
[*][B][COLOR=#FFD700]Custom Symbols:[/COLOR][/B] [COLOR=#AAAAAA]Each currency can have a custom chat symbol configured under [/COLOR][COLOR=#E0E0E0]currency-exchange.symbols[/COLOR][COLOR=#AAAAAA] (e.g. [/COLOR][COLOR=#E0E0E0]Gems: "&a✦"[/COLOR][COLOR=#AAAAAA], [/COLOR][COLOR=#E0E0E0]Tokens: "&b✪"[/COLOR][COLOR=#AAAAAA]). Falls back to the currency name if not defined.[/COLOR]
[*][B][COLOR=#FFD700]Auto-Convert:[/COLOR][/B] [COLOR=#AAAAAA]If a player lacks funds in a specific currency, VaultX automatically deducts the equivalent from their default currency using the configured exchange rate ([/COLOR][COLOR=#E0E0E0]auto-convert: true[/COLOR][COLOR=#AAAAAA]).[/COLOR]
[*][B][COLOR=#FFD700]Exchange Rates:[/COLOR][/B] [COLOR=#AAAAAA]Each currency's value is defined relative to the default currency. Example: 1 Gem = 1000 coins, 1 Token = 10 coins.[/COLOR]
[*][B][COLOR=#FFD700]Redis-Backed:[/COLOR][/B] [COLOR=#AAAAAA]Custom currency balances are stored in Redis hashes ([/COLOR][COLOR=#E0E0E0]vaultx:balances:[uuid][/COLOR][COLOR=#AAAAAA]) and mirrored to the local database.[/COLOR]
[/LIST]

[B][COLOR=#FFFFFF]Dynamic Exchange Rates (Forex Engine):[/COLOR][/B]
[COLOR=#AAAAAA]VaultX includes a live Forex engine that makes currency exchange rates fluctuate dynamically over time:[/COLOR]
[LIST]
[*][COLOR=#AAAAAA]Rates update every [/COLOR][COLOR=#E0E0E0]update-interval-minutes[/COLOR][COLOR=#AAAAAA] (default: [B]15 min[/B]) by a configurable [/COLOR][COLOR=#E0E0E0]max-fluctuation-percent[/COLOR][COLOR=#AAAAAA] (default: [B]3.5%[/B]).[/COLOR]
[*][COLOR=#AAAAAA]A [/COLOR][COLOR=#E0E0E0]demand-factor[/COLOR][COLOR=#AAAAAA] (default: [B]0.001[/B]) adjusts rates based on traded volumes — high demand pushes rates up.[/COLOR]
[*][COLOR=#AAAAAA][B]Market Events[/B] (Crash, Boom, Shortage) can fire randomly with a configurable [/COLOR][COLOR=#E0E0E0]chance-percent[/COLOR][COLOR=#AAAAAA] (default: [B]10%[/B]) per interval.[/COLOR]
[/LIST]

[CENTER][SIZE=5][B][COLOR=#FFD700]🏦  7.  NATIVE BANK SYSTEM[/COLOR][/B][/SIZE][/CENTER]

[B][COLOR=#FFFFFF]1. Listen to Transactions Asynchronously:[/COLOR][/B]
[COLOR=#AAAAAA]VaultX fires a [B]VaultTransactionEvent[/B] asynchronously on every deposit and withdrawal, allowing other plugins to audit or react to economy behavior with zero performance penalty.[/COLOR]

[CODE=java]
import net.milkbowl.vault.economy.events.VaultTransactionEvent;
import org.bukkit.event.EventHandler;
import org.bukkit.event.Listener;

public class MyEconomyAuditor implements Listener {

    @EventHandler
    public void onVaultTransaction(VaultTransactionEvent event) {
        String type = event.getType().name(); // DEPOSIT or WITHDRAW
        String player = event.getPlayerName();
        double amount = event.getAmount();
        // The package/plugin namespace that triggered the transaction (e.g. "fr.skynex")
        String callerPlugin = event.getCallerPlugin();

        System.out.println("[Audit] " + type + " of $" + amount + " for " + player + " by " + callerPlugin);
    }
}
[/CODE]

[B][COLOR=#FFFFFF]2. Async Economy API (Non-blocking):[/COLOR][/B]
[COLOR=#AAAAAA]VaultX exposes async wrappers for all core economy operations via the [B]VaultAsyncEconomy[/B] interface without blocking the main server thread:[/COLOR]
[CODE=java]
import net.milkbowl.vault.economy.VaultAsyncEconomy;

if (vaultEcon instanceof VaultAsyncEconomy) {
    VaultAsyncEconomy asyncEcon = (VaultAsyncEconomy) vaultEcon;

    asyncEcon.getBalanceAsync(player).thenAccept(balance -> {
        System.out.println("Balance: " + balance);
    });

    asyncEcon.depositPlayerAsync(player, 1000.0).thenAccept(response -> {
        if (response.transactionSuccess()) {
            System.out.println("Deposit OK! New balance: " + response.balance);
        }
    });
}
[/CODE]

[B][COLOR=#FFFFFF]3. Multi-Currency API:[/COLOR][/B]
[COLOR=#AAAAAA]Interact with custom currencies like Gems or Tokens defined in VaultX by casting the economy service to [B]MultiCurrencyEconomy[/B]:[/COLOR]
[CODE=java]
import net.milkbowl.vault.economy.MultiCurrencyEconomy;

if (vaultEcon instanceof MultiCurrencyEconomy) {
    MultiCurrencyEconomy multiEcon = (MultiCurrencyEconomy) vaultEcon;

    // Get balance of a custom currency
    double gemsBalance = multiEcon.getCurrencyBalance(player, "gems");

    // Deposit custom currency
    multiEcon.depositCurrencyPlayer(player, "gems", 100.0);
}
[/CODE]
